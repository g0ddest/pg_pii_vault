# Contributing

## Development environment

- Rust stable (CI uses the version in `.github/workflows/pr-validation.yml`).
- `cargo-pgrx` **0.16.1** exactly — it must match the `pgrx` version pinned in
  `Cargo.toml`:

  ```bash
  cargo install cargo-pgrx --version 0.16.1 --locked
  cargo pgrx init            # or --pg18=/path/to/pg_config for an existing server
  ```

- Docker, to run a Vault dev server for the real-Vault tests, and `jq`
  (used by the scripts in `scripts/ci/`).

## Tests

```bash
cargo pgrx test pg18       # any of pg14 .. pg18
```

The tests run inside a temporary PostgreSQL cluster that preloads the
extension. Vault behaviour is covered by an in-process fake server
(`src/tests/fake_vault.rs`), including failures, timeouts, cancellation and
redirects. To also run the end-to-end tests against a real Vault, start a dev
server and create least-privilege tokens from `vault/policies/`:

```bash
docker run -d --name vault-dev -p 8200:8200 --cap-add=IPC_LOCK \
  -e VAULT_DEV_ROOT_TOKEN_ID=root hashicorp/vault:2.1.1 server -dev
eval "$(scripts/ci/setup-vault.sh | sed 's/^/export /')"
cargo pgrx test pg18
```

`setup-vault.sh` mounts Transit, installs the policies and prints
`PII_VAULT_TEST_URL`, `PII_VAULT_TEST_TOKEN` (export mode),
`PII_VAULT_TEST_TRANSIT_TOKEN` (transit mode) and `PII_VAULT_TEST_ADMIN_TOKEN`
(used only to rotate keys). The real-Vault tests are skipped when
`PII_VAULT_TEST_URL` is not set.

If the repository lives under a long path, set `CARGO_PGRX_TEST_PGDATA` to a
short directory: the test cluster's Unix socket path must stay under 103 bytes.

## Checks run by CI

```bash
cargo fmt --all -- --check
cargo clippy --locked --no-default-features --features "pg18 pg_test" --all-targets -- -D warnings
cargo deny check advisories bans licenses sources
scripts/ci/upgrade-test.sh 18      # needs a Vault reachable at PII_VAULT_TEST_URL
scripts/ci/docker-smoke.sh         # builds the image and runs the demo stack
```

## Changing the SQL interface

The install script is generated by pgrx from the Rust code. Existing
installations are upgraded with hand-written scripts in `sql/`
(`pg_pii_vault--<old>--<new>.sql`), which `cargo pgrx install/package` ship
alongside the generated script. When a release changes any SQL object
(function markings, new functions, casts, privileges):

1. bump `version` in `Cargo.toml`;
2. add `sql/pg_pii_vault--<previous>--<new>.sql` that turns the previous
   release's catalog into the new one;
3. run `scripts/ci/upgrade-test.sh` with `PREV_REF` set to the previous
   release tag — it fails unless the upgraded catalog equals a fresh install.

Stored values must stay readable by every later version: never change the
meaning of an existing format; add a new format version instead
(see `src/contents.rs`).

## Releasing

1. Update `CHANGELOG.md` (replace `Unreleased` with the release date) and the version in `Cargo.toml`.
2. Tag `vX.Y.Z` and publish a GitHub release.
3. The `Release` workflow attaches extension tarballs for PostgreSQL 14–18 on
   amd64 and arm64 (with SHA-256 sums and provenance attestations) and pushes
   the multi-arch image to `ghcr.io` (with SBOM and provenance).
